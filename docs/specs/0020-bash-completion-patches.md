# 0020 — Remove bash completion patches from Nix packaging

**Status:** implemented
**App:** yb
**Implemented in:** 2026-05-05

## Problem

`nixpkgs/pkgs/by-name/yb/yb/package.nix` applies two `substituteInPlace`
patches to the generated bash completion script at install time:

1. Inject `compopt -o filenames` so that path arguments complete correctly
   (without it, bash adds a space after a directory match instead of
   continuing into the directory).
2. Replace `words[COMP_CWORD]="$2"` with a `COMP_LINE`/`COMP_POINT`-based
   expression so that arguments containing spaces (e.g.
   `--reader "Yubico YubiKey OTP+FIDO+CCID 00 00"`) complete correctly.

Both patches are fragile: they match on exact generated output and will
silently stop applying if `clap_complete` changes its template.

Investigation shows both issues are already addressed upstream:

- **Patch 2** (`COMP_LINE`/`COMP_POINT`): fixed in `clap_complete` 4.4.6
  (January 2024) for bash ≥ 4. The fix is gated on `${BASH_VERSINFO[0]} -ge 4`
  and is present verbatim in the script generated by `clap_complete` 4.6.0
  (the version yb currently uses). The patch is a no-op on bash 4+.

- **Patch 1** (`compopt -o filenames`): fixed in `clap_complete` 4.4.9
  (January 2024) for arguments annotated with `ValueHint::FilePath` or
  `ValueHint::DirPath`. However, yb uses the dynamic completion engine
  (`CompleteEnv` + `ArgValueCompleter`/`PathCompleter`), not the static
  `Shell::Bash` generator. The dynamic engine already handles path completion
  natively — `PathCompleter::file()` and `PathCompleter::dir()` produce the
  correct `compopt` calls without needing the hint. The patch targets the
  static generator's output and may not match the dynamic engine's script.

## Goals

- Verify that both patches are no-ops against the `clap_complete` 4.6.0
  dynamic-engine output (check substitution actually matches).
- If confirmed no-ops: remove both `substituteInPlace` patches from
  `package.nix`.
- Verify that bash completion still works correctly after removal (path
  completion, space-containing reader names).

## Non-goals

- Fixing completion for bash < 4 (macOS ships bash 3; that is a separate
  concern).
- Patching `clap_complete` upstream (already fixed there).
- Changing yb's CLI argument definitions.

## Specification

### Empirical verification (2026-05-05)

Generated the raw bash completion script from the installed `clap_complete`
4.6.0 dynamic-engine binary:

```
YB_COMPLETE=bash yb > /tmp/yb_raw.bash
```

**Patch 1 (`compopt -o filenames`):** The raw script contains no `compopt -o
filenames` call. The pattern `    ) )` (after COMPREPLY is set) is present and
the substitution matches. **Patch is active and necessary.**

**Patch 2 (`COMP_LINE`/`COMP_POINT`):** The raw script contains
`words[COMP_CWORD]="$2"` inside the bash-4 guard, not the fixed
`COMP_LINE`/`COMP_POINT` expression. The substitution matches. **Patch is
active and necessary.**

Root cause: `clap_complete` 4.4.6/4.4.9 fixed these bugs in the **static**
bash generator (`Shell::Bash`), but the **dynamic engine** (`CompleteEnv`)
uses a separate bash glue script template that has not received the same fixes.
These are two independent code paths in `clap_complete`.

**Conclusion for Patch 2 (`COMP_LINE`/`COMP_POINT`):** Active and necessary.
Upstreamed as a fix to `clap_complete/src/env/shells.rs`; see
https://github.com/clap-rs/clap/issues/6363 and associated PR.

**Conclusion for Patch 1 (`compopt -o filenames`):** Active and matches, but
adding `compopt -o filenames` unconditionally is wrong. The dynamic engine's
`PathCompleter` already appends a trailing `/` to directory candidates. Bash
then sees `compopt -o filenames` and appends another `/`, producing double
slashes (`proc-macro-srv103ca-0//`). The fix cannot be unconditional.

The correct upstream fix for Patch 1 requires the Rust completer to signal
back to the glue script whether any candidate is a file path — something the
current architecture does not support. Patch 1 must remain in `package.nix`
for now.

## Open questions

- How should `compopt -o filenames` be conditioned in the dynamic engine?
  One approach: have the Rust side emit a sentinel candidate (e.g. a special
  IFS-delimited token) to indicate file-path mode; the glue script checks for
  it. Needs upstream design discussion.
